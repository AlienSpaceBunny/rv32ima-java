# Timer/counter phase: bench against 0.1.8 (2026-10-12)

Evidence for step T7 of [the implementation plan](../../../TIMER_AND_ATTEMPTS_IMPLEMENTATION_PLAN.md):
`main` at `1c82200` (T1–T6) against the `v0.1.8` tag, on HotSpot and Native Image, uncached and
with a 4096-slot decoded cache. **Both regressions below were accepted** (Nate, 2026-10-12); V-32
will choose its execution mode once the core is stable. Nothing was changed in response.

## Summary

- **Batched native work is unchanged.** Per-image medians of HEAD/0.1.8 time are 0.97–1.02×
  on every native image, cached and uncached, outside `reg-ap-step1`.
- **`step(count=1)` is slower** (`reg-ap-step1`, V-32's current AP shape):
  - native: median 1.12×, range 0.98–1.17× over all images and buses (`bytearray`: 12.75 →
    14.67 ns per instruction on `mono`, 9.53 → 11.01 with the cache);
  - HotSpot uncached: median 1.12× in the full matrix and 1.09× in the rerun, up to 1.22×;
    cached: 1.02× median (0.90–1.11×).
  - **Cause:** the design's per-call cost. Each call now samples the `MachineTimeSource` (an
    interface call and an `AtomicLong` read here), recomputes MTIP, and does the larger entry
    work of T3–T6. That is about 1–2 ns per call, which `count=1` pays per instruction. The
    execution API (phase A) is the planned answer: `stepAttempts` samples once per call, not
    per attempt.
- **HotSpot uncached batched work is about 5% slower:** median 1.076× in the full matrix and
  1.055× in a JVM-only rerun. The core-free `host-*` control is 1.00× in both, so it is the core,
  not the machine. Cached HotSpot is 1.00×. Ranges overlap in most cells (HotSpot spread is
  5–50%), so this is a small, probable effect, not a precise figure. A likely contributor is
  `step()`'s growth (native code 0x4fe1 → 0x59c1 bytes) affecting C2's compilation of it.
- **Loops stay unswitched.** Symbolized `mono-bytearray` images built with
  `-H:-DeleteLocalSymbols`: `step()` keeps 6 `ByteArrayBus.readInt` call sites and `runCached()`
  2, as in 0.1.8 ([`unswitching.txt`](unswitching.txt)). T6's extra live `long`
  (`retiredBase`) shows no measurable batched cost on native.

## Method

- **Host and toolchain:** as in [the CPU review evidence](../../2026-10-10/README.md#method):
  i9-13950HX, `taskset -c 2,3`, Corretto 25.0.4.1, GraalVM CE 25.3.4.1 (O2 unless labelled
  `-o3`; `poly-v2`/`-v3` are `-march` variants). Nothing else ran during measurement.
- **Builds:** both bench jars were built with `./mvnw -pl bench -am package -DskipTests` from
  `git archive` exports of `v0.1.8` and `1c82200`, so the working tree did not affect them. Each
  version's bench uses its own API: 0.1.8 passes `elapsedUs`, HEAD a `ManualTimeSource`.

  | Version | Jar SHA-256 |
  | --- | --- |
  | `v0.1.8` | `2be3ab05535f8db39f531f030149655ca227637b855e8eca8f0f157ab16de51e` |
  | `1c82200` | `18eeeb4b45dcfa70cf429aa2a76f2ea463deba75275c66f744c2c14d90590183` |

- **Matrix:** `run_matrix.py --decoded-cache 4096`, all images and buses: two forks of 3
  measured rounds after ≥10 s of warmup, 6 samples per cell, every invocation verified. `v018`
  ran 12:41–13:11 PDT and `head` 13:11–13:42. The JVM rerun (`--only jvm`) ran afterwards for
  both versions.
- **Tables:** [`comparison.md`](comparison.md) (full matrix) and
  [`comparison-jvm-rerun.md`](comparison-jvm-rerun.md), generated by
  [`t7compare.py`](t7compare.py). "Ranges overlap" counts cells whose min–max ranges intersect.
  The run directories are copied verbatim from the git-ignored `bench/out/results/`.
